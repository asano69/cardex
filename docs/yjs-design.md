
# Yjs リアルタイム共同編集の設計

## 概要

各カード（`cards`コレクションのレコード）の本文は、[ygo](https://github.com/reearth/ygo)の
websocketプロバイダを使ってリアルタイムに同期される。ルーム名はカードのidそのもの
（`NoteEditor.tsx`参照）で、同じカードを開いている全クライアントが1つのYjsドキュメント
を共有する。

このドキュメントは以下の2点を記録する。

1. 現在のルーム管理・永続化アーキテクチャ
2. 過去に採用していた「フルスナップショット方式」から現在の「増分ログ方式」に
   切り替えた理由

## ルーム管理（`internal/serve/handler.go`）

- `yjsServer`は`yjsws.Server`のシングルトンで、`initYjsServer`が最初のリクエスト時に
  一度だけ生成する。
- `GET /yjs/{room}`がwebsocketエンドポイント。`{room}`は任意のクライアント指定文字列
  だが、実運用上は常にカードのidと一致する。
- **認証は未実装。** 誰でも任意のルームに接続できる状態なので、本番運用前には
  `RequireSuperuserAuth`相当のガードを websocket ハンドシェイクに追加する必要がある
  （TODOとしてコードにも残っている）。

## 永続化（`internal/serve/ydoc.go`）

### コレクション: `ydoc_updates`

一般的なYjs永続化アダプタ（y-leveldb, y-mongodb, y-redis等）と同じ「増分アップデート
のログを蓄積して再生する」パターンを踏襲している。

| フィールド | 型 | 内容 |
|---|---|---|
| `card` | relation → cards（cascadeDelete） | どのカードのルームか |
| `data` | file | 1回分の差分バイナリ（`doc.EncodeStateAsUpdate()`相当の増分） |
| `created` | autodate | 適用順の並び替えに使用 |

### `LoadDoc`

ルームへの最初の接続時に呼ばれる。`card`で絞り込んだ`ydoc_updates`レコードを
`created`昇順で全件取得し、

- 0件 → ルームは空のドキュメントから開始
- 1件 → その差分バイナリをそのまま返す
- 2件以上 → `mergeUpdates`で`crdt.New()`にすべて`ApplyUpdate`し直し、
  `EncodeStateAsUpdate()`で1つの差分にまとめて返す

### `StoreUpdate` / `StoreUpdateContext`

ygoの永続化ワーカーから呼ばれる。デバウンス（`Server.PersistCoalesceWindow` /
`PersistCoalesceMaxWait`、デフォルト2秒/10秒）はygo側がすでに行っているので、
この関数は単純に「渡された差分バイトをそのまま新規レコードとして`create`する」
だけでよい。これが増分ログ方式の核心で、書き込みコストは編集内容（差分サイズ）に
比例し、ドキュメント全体のサイズには依存しない。

`StoreUpdateContext`はシャットダウン時にygoが優先して使う変種で、`ctx`が
キャンセルされた場合は書き込み前に中断する。

### コンパクション（`compactIfNeeded`）

差分ログは放置すると無限に増え続けるため、`compactionThreshold`（現在200件）を
超えたタイミングで以下を行う。

1. そのルームの生存中ドキュメント（`yjsServer.GetDoc(room)`）を取得
   - ルームが誰にも接続されておらずメモリ上に存在しない場合は何もしない
     （次回の`StoreUpdate`時に再判定される）
2. その時点のドキュメント全体を`EncodeStateAsUpdate()`でエンコードし、
   1件の新規レコードとして保存
3. 圧縮前の全レコードを削除

ポイントは、生存中ドキュメントはこれまでの全差分がすでにマージ済みの状態なので、
新たなマージ処理を書く必要がなく、既存の`EncodeStateAsUpdate()`をそのまま
「圧縮後の1差分」として使い回せること。

### カード削除時の後始末（`forgetRoom`）

`cards`レコードが削除されると、`OnRecordAfterDeleteSuccess("cards")`フックが
`forgetRoom`を呼び、メモリ上のルームを閉じる。紐づく`ydoc_updates`レコードは
`card`フィールドの`cascadeDelete`設定により自動的にカスケード削除される。

### シャットダウン

`app.OnTerminate()`で`yjsServer.Shutdown(ctx)`を呼び、10秒のタイムアウト内で
バッファ済みの書き込みをフラッシュしてからプロセスを終了する。

## 過去の設計（廃止済み）: フルスナップショット方式

初期実装では、`StoreUpdate`に渡ってくる差分バイトを無視し、毎回
`doc.EncodeStateAsUpdate()`でルーム全体の状態を再エンコードして、
`cards.ydoc`という単一のfileフィールドに丸ごと上書き保存していた。

### 採用していた理由（シンプルさ）

- 保存先が「カード1件につきファイル1つ」で完結し、コレクションを増やさずに済む
- ロード処理が単純（ファイルを読むだけ、マージ処理不要）
- 無駄な書き込みを防ぐため`lastSnapshot`（`sync.Map`）で直前の保存バイト列と
  比較し、変化がなければスキップしていた

### やめた理由

1. **保存コストがドキュメントサイズに比例する**
   `EncodeStateAsUpdate()`は毎回ドキュメント全体をシリアライズするため、
   1文字の編集でも保存が走ればノート全体分のバイト列を書き込むことになり、
   ノートが長くなるほど1回あたりのコストが増え続ける。
2. **過去の版が残らない**
   `cards.ydoc`を毎回丸ごと上書きするため、編集履歴やバージョン管理・巻き戻し
   機能を後から追加する余地がなかった。

なお、フルスナップショット自体はYjsの仕様上「正当な差分（update）」であり、CRDTと
してのマージ可能性・複数クライアント間の整合性には問題がなかった。あくまで
「保存コスト」と「履歴」の2点のトレードオフだった。
